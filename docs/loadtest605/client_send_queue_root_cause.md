# 客户端发送队列

日期：2026-10-23。基线 `45d35f7`。工作区里还有未提交的分线变量重名修复。没有改服务器，没有对线上再开一波 605。

## 这轮已经能确定的事

13:47–13:57 的服务器窗口里，Move 处理小于 50ms，回包排队小于 20ms，`reply_soft_drop`、`heartbeat_soft_drop`、Move overload 都是 0。同一时段客户端 8081 发送队列最老一项大约 12.2 秒，机器人心跳超时大约 255 条，权威快照超时大约 13 条。

所以这 12 秒发生在客户端把帧写出去之前，不是服务器把已经生成的回包静默丢掉。

`40ms` 是登录间隔，不是移动频率。移动仍按配置的 2/5/10Hz 发。计划数、忙跳过、入队、确认、超时不是同一批请求，不能加在一起。

## 代码里让队列变老的地方

- 2 秒截止从入队就开始算。帧还排在本连接的发送循环里时，截止已经在走。
- 以前在 `WriteAsync` 之前就把槽标成已写出。面板上的「写出」因此不能证明 socket 写完。
- 每入队一次就 `Release` 一次信号，发送循环醒来却把队列一次排空。多出来的信号会空转。
- 超时记录超过 2048 就整表清空。发送许可以前还看过这张表，清空之后有把已经超时的帧再写出去的风险。
- 连续两次超时就停步，并去要全量快照。快照自己也要排队 12 秒，而且全局只有几个名额。队列已经老的时候，这会把机器人停住。

## 这次改了什么

每个待发送帧带着自己的槽、入队时间和绝对截止。真正开始写之前，槽必须仍是打开的，而且没过截止。过了就跳过，记 `CLIENT_QUEUE_EXPIRED`，不写 socket，也不当服务器超时，也不要快照。

`write_started` 和 `write_completed` 分开。只有 `WriteAsync` 成功返回才算写完。写到一半超时的结果是未知，不会把这条 TCP 拆掉。

一个入队对应一次唤醒，一次唤醒只取一帧。

发送队列里已经有 2 帧，或者最老一帧已经等了 400ms，就不再制造新的 Move。心跳照旧。不在同一条连接上把已经排队的帧调换顺序，避免服务器按到达顺序处理移动时被插队。

写出前过期：位置留在上次确认的地方，下一拍由拥塞控制决定要不要再发。写出后未知：停步，等同一条连接上更晚的 `MoveRsp.state_seq`。满 3 次未知才允许一次全量快照，而且最多等 250ms 的名额，等不到就再退避。协议里没有只含自己坐标的查询，`MapPingRsp` 也没有坐标，所以没有新造字段。
