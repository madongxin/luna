# 客户端和服务器各自能解释的时段

这不是一次新的 605 人抓包。时间线用的是 2026-10-23 已有截图和源码审查，缺的格子写未知。

| 阶段 | 客户端现在能看到的 | 服务器侧 | 这次窗口的结论 |
| --- | --- | --- | --- |
| 计划发送 | `move_planned` | 还没收到 | 上一轮计划数远大于入队数，因为机器人在等上一发 |
| 入队 | `queue_accepted`。以前的「发出」是这个数 | 未知 | 72096 是入队尝试，不是 TCP 写出 |
| Socket 写出 | `write_completed` / 每秒写出 | Gateway 入站 | 上一轮没有这个计数。监控入站大约每秒数千字节，精确帧数未知 |
| 服务器生成回包 | 看不到 | `rsp_generated`，审查里提到可能软丢 | `reply_soft_drop` 和 `heartbeat_soft_drop` 的窗口增量未知。不能据此说 37580 次超时都是软丢 |
| Socket 写出回包 | 看不到 | 发送缓冲、kernel sendq | 截图里 sendq 接近 0，不足以单独证明内核堵死 |
| 客户端收到帧 | `FramesDecoded` | 未知 | 未在上一轮分开记录 |
| 匹配到待响应 | `rsp_matched` / `PendingHit` | 未知 | 权威确认 34103。拒绝 0 |
| 迟到 | `Late`。不再进入 Push | 未知 | 上一轮晚到的回包会被当成推送。这一轮起不再这样 |
| 超时 | 2 秒到点，并区分写出前/写出后 | 未知 | 37580。413 = 72096 - 34103 - 37580，是截图当时仍在途 |
| 可靠 Push | 只在连续 `server_seq` 应用后更新 | AOI 合并、PushBatch | `client_seq` 490 和 `server_seq` 362 不是同一条序号，不能相减 |
| 快照恢复 | 空列表或不通过 epoch/实例校验时保持「视野未恢复」 | 快照上限、空列表是否真实 | 曾出现 `ok=true` 且 `aoi=0`。当时不能当成周围没人 |

建议的下一轮仍是分开跑：只心跳、多线移动、同一实例里的合法密度。每一轮都要同时有客户端的入队/写出/匹配/晚到，和两台 Gateway 的 soft-drop 增量。没有这些数之前，不把某一方写成唯一原因。
